# Lab 001：ECS 架构与基本概念

## ECS 是什么

ECS（Entity-Component-System，实体-组件-系统）是一种以数据组织方式为中心的软件架构。它把传统对象中的“身份”“数据”和“行为”拆开：

- **Entity（实体）**：一个稳定的、通常很小的身份标识，例如整数 ID。实体本身不负责保存复杂业务数据。
- **Component（组件）**：只描述一类数据，例如位置、速度、生命值、可渲染标记。组件一般不包含处理这些数据的业务方法。
- **System（系统）**：处理数据的逻辑。系统声明自己需要读取或修改哪些组件，然后批量处理满足条件的实体。

ECS 并不属于某一个游戏引擎，也不只用于游戏。它适合拥有大量相似对象、需要频繁更新数据、并且希望把数据处理拆成多个阶段的程序，例如游戏、物理模拟、粒子系统、机器人、可视化和实时仿真。

这里的“系统”不是面向对象中的对象实例，而更接近一个对数据集合执行变换的处理步骤。对象的能力由组件组合决定，而不是由继承层次决定。

## 与典型 OOP 对象模型的区别

以下是两种常见的组织方式。它们不是互斥的语言特性，而是两种不同的默认数据和行为组织思路。

### 典型 OOP 的对象导向布局

在典型 OOP 设计中，一个对象把状态和方法放在一起：

```text
class Player:
    position
    velocity
    inventory
    render_state

    update()
    render()
    take_damage()
```

程序通常持有许多 `Player*`、`Enemy*` 或基类指针，再逐个调用对象的方法。真实内存布局取决于语言和实现，但大型对象常见以下特征：

1. 对象可能分别分配在堆上，数组中保存的是指针而不是对象数据本身。
2. 同一处理步骤关心的字段（例如所有对象的位置）可能散落在不同对象和不同缓存行中。
3. 对象带有不参与当前处理的冷数据，例如背包、音频状态或脚本引用，读取对象时也可能把这些无关字段带入缓存。
4. 通过继承和虚函数调用时，实际类型和方法目标可能在运行时才能确定，处理循环更难被编译器批量优化。
5. 一个对象的方法可能间接访问其他对象，数据访问范围不容易从调用点看出来。

这些问题不是 OOP 必然产生的结果。OOP 也可以使用连续数组、数据导向设计和批量算法；这里比较的是“对象各自拥有数据并逐个调用方法”这一常见布局与 ECS 的典型布局。

### ECS 的数据布局

ECS 通常把组件按类型集中存储，并通过实体 ID 关联这些组件：

```text
Position: [p0, p1, p2, p3, ...]
Velocity: [v0, v1, v2, v3, ...]
Health:   [h0, h1, h2, h3, ...]

Entity 0 -> Position[0], Velocity[0]
Entity 1 -> Position[1]
Entity 2 -> Position[2], Health[2]
```

不同实现的具体布局并不完全相同：

- **SoA（Structure of Arrays）**：每种组件的字段或每个组件类型单独形成数组，特别适合“只处理某一两个字段”的批量循环。
- **AoS（Array of Structures）**：同一实体的一组组件字段放在一起，适合总是同时访问这些字段的处理。
- **Archetype/Chunk（原型/数据块）**：拥有相同组件集合的实体放进同一组数据块。查询某组组件时只遍历匹配的块。
- **Sparse Set（稀疏集合）**：用稀疏索引和紧凑数组维护组件，适合组件频繁添加、删除或查询的场景。

因此，“ECS 的内存设计”不是只有一种固定实现，但核心目标通常是：让相同处理步骤需要的数据尽量连续、紧凑，并减少无关数据和指针跳转。

## 为什么内存布局可能更快

### CPU 缓存局部性

处理器访问内存时，通常不是只取一个字段，而是以缓存行（cache line）为单位把附近的一段内存带入缓存。如果程序连续访问 `Position` 数组，第一次访问后，后续相邻位置很可能已经在更快的缓存中：

```text
for each position in positions:
    position.x += speed * delta_time
```

这样的循环可以顺序读取，减少随机内存访问和缓存未命中。相反，如果位置分散在很多堆对象中，处理器可能在每个对象之间跳转，等待内存的时间会增加。

### 减少无关数据

移动系统只需要位置和速度，不需要实体的背包、渲染资源、脚本状态等字段。ECS 可以只遍历 `Position` 和 `Velocity`，避免把不参与本次计算的数据带入缓存。缓存空间有限，保留有效数据越多，后续访问越可能命中。

### 批量循环、SIMD 与预取

连续且类型稳定的数据循环更容易被编译器优化，也更容易使用 SIMD 指令一次处理多个值。运行时或容器还可以预取后续数据。若每次处理都要通过指针找到不同动态类型的对象，这些优化机会会减少。

### 更少的间接调用

系统通常是一个已知的处理函数，对一组确定类型的数据循环执行；它不必对每个实体动态分派一个方法。这样可以降低间接调用成本，并让编译器更清楚循环的读写范围。

这些优势描述的是“典型 ECS 数据导向布局”相对于“分散的对象图”的潜在优势，并不是说只要把类改名为组件就会自动获得性能。组件布局、查询实现、实体数量、删除迁移成本和实际访问模式都会影响结果；性能结论应通过目标程序的测量验证。

## ECS 如何支持多处理器并行执行

这里的并行是指多个处理器核心（或多个硬件线程）在同一时间处理不同工作，不是泛指异步、任务切换或“并发”这个宽泛概念。

ECS 适合并行的关键，不只是组件连续，而是系统的读写范围可以显式表达。调度器可以为每个系统建立访问集合：

```text
MovementSystem:
    读取 Velocity
    读写 Position

DamageSystem:
    读取 Collision
    读写 Health

RenderPreparationSystem:
    读取 Position、Renderable
    写入 RenderQueue
```

如果两个系统访问的数据没有冲突，调度器可以把它们分派到不同处理器核心：

```text
时间轴 ─────────────────────────────────────>
核心 0: [MovementSystem] [RenderPreparationSystem]
核心 1: [DamageSystem  ]
核心 2: [ParticleSystem]
```

例如 `MovementSystem` 只写 `Position`，`DamageSystem` 只写 `Health`，两者可以同时执行。若一个系统写 `Position`，另一个系统读 `Position`，调度器必须建立先后关系，或者使用明确的阶段、快照和消息传递，不能为了并行而产生数据竞争。

### 依赖图与调度

系统可以被抽象成带读写标记的节点。若系统 A 的写集合与系统 B 的读集合或写集合相交，就存在依赖边：

```text
A 写 Position ─────> B 读 Position
C 写 Health   与    A 读 Position 不冲突，可并行
```

调度器据此把系统组织成多个阶段或任务组。一个阶段中的无冲突系统可以同时执行，依赖完成后再开始下一阶段。这样，程序员不必为每个实体手写线程分配，也能让框架根据数据关系安排工作。

### 并行访问仍然有边界

ECS 不会消除所有同步成本：

- 两个系统写同一组件时通常不能直接并行。
- 一个系统新增、删除组件，可能导致实体在数据块之间迁移，需要在安全点执行。
- 多个核心写入同一缓存行可能产生 false sharing（伪共享）。
- 系统之间若共享全局资源，仍需要锁、分阶段访问或其他同步策略。
- 把很小的工作拆成大量任务，调度和同步开销可能超过并行收益。

所以 ECS 提供的是“更容易分析和调度的数据依赖”，而不是无条件的多核加速。

## ECS 如何实现解耦

ECS 的解耦主要来自三个方向。

### 组件与系统解耦

组件只定义数据，不需要知道谁会使用它；系统只依赖自己声明的组件，不需要知道实体的完整类型。例如 `MovementSystem` 可以处理玩家、敌人、投射物和摄像机，只要它们拥有 `Position` 与 `Velocity`：

```text
MovementSystem(Position, Velocity)
    -> 处理所有同时拥有这两个组件的实体
```

新增一个会移动的实体类型时，只需组合这些组件，不必继承某个庞大的基类，也不必修改移动系统。

### 通过组合代替继承

对象的能力可以通过组件组合表达：

```text
玩家      = Player + Position + Velocity + InputControlled + Renderable
敌人      = Enemy + Position + Velocity + Health + AIControlled + Renderable
投射物    = Stone + Position + Velocity + Damage + Lifetime
```

这些实体共享位置和速度系统，但不需要位于同一继承树中。添加 `Frozen`、`Hidden` 或 `Invulnerable` 等组件，也可以让系统通过查询条件改变处理范围。

### 系统之间通过数据和阶段连接

系统不必直接持有另一个系统的对象引用。一个系统写入组件、事件或命令，另一个系统在自己的阶段读取它们：

```text
CollisionSystem  -> 产生 DamageEvent
DamageSystem     -> 读取 DamageEvent，修改 Health
DeathSystem      -> 查询 Health == 0，添加 Dead
CleanupSystem    -> 查询 Dead，移除或回收实体
```

每个系统拥有较小而明确的职责，系统之间通过公开的数据契约连接。这样可以单独替换渲染、输入、AI 或存档系统，也更容易测试一个系统对一组组件数据的处理结果。

## 通用使用流程

下面是与具体语言和框架无关的完整伪代码：

```text
定义组件 Position { x, y }
定义组件 Velocity { x, y }
定义组件 Health { value }

创建实体 player
    添加 Position(0, 0)
    添加 Velocity(1, 0)
    添加 Health(100)

定义 MovementSystem:
    查询 Position + Velocity
    对每个匹配实体:
        position += velocity * delta_time

定义 DamageSystem:
    读取 DamageEvent
    根据事件查找目标实体
    修改目标的 Health

定义 DeathSystem:
    查询 Health 且 value <= 0
    为匹配实体添加 Dead

每个更新周期:
    收集输入和事件
    按读写依赖调度可并行的系统
    执行系统
    提交新增、删除和组件变更
```

## 这种设计的优势与代价

### 优势

1. **数据局部性好**：相同组件可以紧凑存储，减少随机指针跳转和缓存未命中。
2. **批处理效率高**：系统按组件集合工作，适合循环优化、SIMD 和数据预取。
3. **更容易利用多核**：系统的读写集合可以生成依赖图，让无冲突系统在多个处理器核心上同时执行。
4. **组合灵活**：实体能力由组件组合决定，减少继承层次和大型基类。
5. **职责清晰**：组件是数据，系统是处理逻辑，系统之间通过数据、事件和阶段连接。
6. **便于扩展和测试**：新增功能通常是新增组件或系统；系统也可以用一组独立的组件数据进行测试。

### 代价

1. 需要学习查询、生命周期、数据迁移和系统调度等概念。
2. 组件添加或删除可能导致数据移动，频繁结构变化需要合适的存储策略。
3. 调试时不再是“找到一个对象并调用方法”，需要从实体、组件和系统之间追踪行为。
4. 系统之间的隐式依赖如果没有声明清楚，可能产生顺序错误或同步问题。
5. 对象数量很少、对象关系复杂或行为高度依赖自身状态的程序，采用 ECS 未必比简单 OOP 更合适。

## 本实验关注点

- 区分实体的身份、组件的数据和系统的行为。
- 理解典型对象布局与数据导向布局在缓存访问上的差异。
- 理解 ECS 如何通过明确的读写集合支持多个处理器核心并行执行。
- 理解组件组合和数据契约如何减少模块之间的直接引用。
- 认识到 ECS 是一种可由不同框架和引擎采用的架构，后续实验再将这些通用概念映射到具体实现。

## Bevy 中最基础的 ECS

前面的内容是通用 ECS 概念。Bevy 为这些概念提供了具体的 Rust 类型。这里先只介绍 Bevy 对 E、C、S 和 `World` 的对应关系；具体的查询、创建、修改和调度 API 留到后续 lab。

### Bevy 中的 E、C、S

- **Entity（实体）**：Bevy 的 `Entity` 是一个唯一标识符，用来指向某个 `World` 中的实体记录。它不是实体的全部数据，也不是一个包含业务字段的对象；位置、速度、生命值等数据都由组件提供。
- **Component（组件）**：实现 `Component` 的 Rust 类型，表示附着在实体上的一类数据。例如 `Position`、`Velocity` 和 `Health` 都可以是组件。一个实体对同一种组件类型通常最多拥有一个值。
- **System（系统）**：由 Bevy 执行的处理逻辑，负责根据组件数据完成移动、输入、渲染准备或其他业务操作。系统本身是逻辑，不是实体或组件数据。

### `World` 中保存什么

在 Bevy ECS 中，`World` 是 ECS 运行时数据的主要容器。它管理：

```text
World
├── Entity 元数据和生命周期信息
├── Component 类型注册信息
├── 各实体的 Component 数据
└── ECS 存储和查询所需的内部元数据
```

组件数据并不是简单地作为一个 `HashMap<Entity, Component>` 暴露出来。Bevy 会根据组件集合和存储类型组织数据，`World` 负责维护实体与这些组件数据之间的关系。应用代码通过 Bevy 提供的 ECS API 使用这些数据，而不应直接修改内部存储。

`App` 通常会使用一个主 `World` 保存当前应用的 ECS 状态。可以先把它们理解为：`World` 保存数据，Entity 提供身份，Component 提供数据，System 提供处理这些数据的逻辑。如何创建实体、声明组件访问、让系统执行，以及如何精确查询或修改某个组件，将在后续 lab 分别展开。
